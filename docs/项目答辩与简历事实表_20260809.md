# eufs 项目答辩与简历事实表

日期：2026-08-09

这份材料只包含当前公开仓库已经实现并验证的事实。它不是功能规划，也不把用户态原型
包装成生产文件系统。

## 1. 项目名称

**openEuler 上的崩溃一致性用户态文件系统与幂等对象服务**

一句话问题定义：

> 在并发请求、客户端超时重试和服务进程崩溃下，让一次对象写入最终只呈现完整旧版本
> 或完整新版本，同时限制排队请求和 payload 占用，并提供可恢复、可检查的磁盘证据。

## 2. 简历可用表述

下面三条应根据简历版面压缩措辞，但不能改变结论边界：

1. 使用 C++17、FUSE3 和自定义磁盘格式实现 direct/single-indirect 文件寻址与通用 COW
   写计划；设计 ordered data + metadata redo WAL、A/B control、COMMIT/replay/checkpoint
   持久化链，在六个同步边界注入进程退出，验证 COMMIT 前恢复旧状态、COMMIT 后恢复
   新状态，并用 `eufsck` 检查 bitmap、目录图、块引用和 Request Ledger。
2. 在 openEuler 24.03 上集成固定版本 Apache brpc，实现基于 attachment 的
   `Put/Get/Stat` 对象接口、异步完成所有权、有界写/读队列、在途 payload 字节准入和
   bvar 指标；16 路并发矩阵分别触发 13 次队列拒绝和 14 次字节拒绝，重启后成功对象
   内容完整、被拒绝对象不存在，最终 `eufsck` 零问题。
3. 将 16-byte Request-ID、请求指纹和对象变更结果写入持久化 Request Ledger，并与对象
   发布纳入同一日志事务；验证服务在六个持久化阶段退出且客户端丢失响应后，同 ID 同请求
   可执行或重放既有结果，同 ID 不同请求被拒绝。当前普通回归为 CTest `46/46`。

不能写：生产级文件系统、完整 POSIX、网络 exactly-once、硬件断电认证、多写 worker
扩展、裸机性能提升或 Apache brpc 上游贡献。

## 3. 90 秒答辩主线

### 0-20 秒：问题与入口

项目有两个入口：FUSE 把普通文件操作送入本地存储内核；brpc 把对象请求送入
`ObjectBackend`。FUSE range-write 与对象 replace 共用 `PrepareFileMutation` 核心，
对象 create 使用 `NewObjectPlan`；两条路径继续共用事务执行、恢复、镜像会话和一致性检查。

### 20-50 秒：核心正确性

不能原地覆盖旧数据，因为 COMMIT 前崩溃会留下“旧 inode 指向已被改坏的旧块”。因此先
分配新块并写完整新数据，`fdatasync` 后才记录 metadata after-image；日志 body、control
和 COMMIT 依次持久化。恢复只信 control 声明范围内且结构、CRC 均合法的事务：COMMIT
前丢弃，COMMIT 后幂等重放 home metadata，再 checkpoint。

### 50-70 秒：重试与并发

RPC 返回前进程可能已经提交，所以客户端看到超时不能判断写入是否发生。Request-ID
不能只放内存；项目把 ID、请求指纹和结果与对象变更放入同一事务。重启后同 ID 同指纹
返回原结果，同 ID 不同指纹拒绝。服务先按 payload 字节准入，再计算 SHA-256，然后进入
有界队列；这样大请求数量和排队任务数量都有独立上界。

### 70-90 秒：证据与边界

六阶段崩溃矩阵证明 COMMIT 前后三个阶段分别恢复旧/新状态；两组 16 路并发矩阵分别隔离
队列门和字节门，之后重启逐 key 校验并运行 `eufsck`。延迟来自 QEMU TCG，只用于发现
“先哈希再拒绝”的准入顺序缺陷，不声称生产性能。当前写事务由单 worker 串行，这是已
验证的一致性边界，不包装成高并发写扩展。

## 4. 六个必须掌握的问题

### 4.1 为什么不是原地覆盖数据块？

**推导：** 假设 inode 仍指向块 42。若先覆盖块 42，再写 journal metadata，进程在
COMMIT 前退出，恢复会保留旧 inode，但所谓旧版本的数据已经被覆盖，old-or-new 语义
失败。COW 让旧 inode 始终指向未修改旧块，新块只有在 COMMIT 后才通过 metadata
after-image 变得可达。

代码入口：[`file_write_plan.cpp`](../src/metadata/file_write_plan.cpp)、
[`journal_transaction_executor.cpp`](../src/journal/journal_transaction_executor.cpp)。

### 4.2 为什么队列上限和字节上限必须同时存在？

**推导：** 只限制任务数时，少量 4 MB 请求仍可占用大量 payload；只限制字节时，海量
小请求仍可堆积任务对象、closure 和等待时间。字节 Lease 约束排队加执行中的 payload，
有界队列约束任务数量。任一准入失败都不能转移任务所有权，Lease 由 RAII 自动归还。

代码入口：[`inflight_byte_limiter.cpp`](../src/rpc/inflight_byte_limiter.cpp)、
[`bounded_task_queue.cpp`](../src/rpc/bounded_task_queue.cpp)。

### 4.3 为什么字节准入放在 SHA-256 前面？

**推导：** SHA-256 对 payload 是线性工作。若先哈希再准入，最终必然被字节门拒绝的
4 MB 请求仍会消耗 CPU，过载门只限制内存却不能保护摘要计算。当前先做廉价字段和格式
上限检查，再取得字节 Lease，随后才哈希；无效摘要请求在哈希期间仍占额度，但占用有界，
这是用受控内存换 CPU 过载保护的明确取舍。

代码入口：[`object_service_impl.cpp`](../src/rpc/object_service_impl.cpp)。

### 4.4 为什么不能宣称 exactly-once？

**推导：** 网络可能永久丢失响应，客户端不能仅凭一次调用结果判断服务端是否提交；
ledger 也只有当前镜像内的固定容量，写满后会拒绝新的 Request-ID，不提供跨镜像或
跨服务实例协议。当前准确表述是：已持久化记录对应的同一 Request-ID 和指纹具有
at-most-once mutation effect，并可确定性重放结果。它不保证消息只传输一次，也不覆盖
尚未实现的 delete/recreate ABA。

代码入口：[`request_ledger_plan.cpp`](../src/object/request_ledger_plan.cpp)、
[`object_backend.cpp`](../src/object/object_backend.cpp)。

### 4.5 COMMIT 已持久化但客户端超时，重试会发生什么？

**推导：** 重启恢复先验证事务并把 metadata after-image 重放到 home；对象和 ledger
记录在同一个 COMMIT 中，所以不会出现“对象已发布但 ID 不存在”。重试命中同 ID 同指纹
时读取既有结果，不再次修改镜像。六阶段矩阵中的 `commit/home-blocks/checkpoint` 均验证
重试前后镜像 SHA-256 不变。

证据入口：[`summary.log`](../evidence/brpc/request_id_crash_matrix_20260808/summary.log)。

### 4.6 为什么当前只有一个写 worker，这算不算玩具？

**结论：** 单 worker 不是高并发卖点，而是当前日志和 `ObjectBackend` 的明确串行化边界。
RPC 接收、校验、哈希、读请求和排队仍可并发；磁盘 mutation 串行执行，避免在尚无并发
日志 reservation、key/inode 锁序和冲突检测时制造数据竞争。项目的竞争力来自完整的
崩溃语义、持久化幂等和可核验证据，不来自虚假的并行写数字。若扩展多写 worker，必须先
设计事务 reservation、冲突域和锁序，并用 TSan 与崩溃矩阵重新证明，当前不在冻结范围。

代码入口：[`object_service_impl.cpp`](../src/rpc/object_service_impl.cpp)、
[`object_backend.cpp`](../src/object/object_backend.cpp)。

## 6. 诚实边界

- FUSE 原型没有完整 POSIX 语义，不支持完整目录变更、稀疏文件或 double-indirect。
- Request Ledger 容量固定；当前无 Delete/tombstone，不覆盖 delete/recreate ABA。
- 受控 `_exit(200)` 证明进程崩溃恢复，不等价于真实掉电或存储设备缓存失效认证。
- 过载矩阵证明资源上界和拒绝隔离，不证明生产吞吐、P99 或横向扩展。
- 项目使用 Apache brpc 和 libfuse3，但当前没有可声称的上游 Issue/PR/merge。
